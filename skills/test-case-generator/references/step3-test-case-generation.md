# Step 3：テストケース生成

## 契約

| 項目 | 内容 |
| --- | --- |
| 入力 | `output/{ID}/step2-viewpoints.md`（ゲート2 で確定したもの）、`output/{ID}/step1-analysis.md`、`PBI/{ID}/`、`.qa/product.md`、`.qa/knowledge/`（画面名・ボタン名・エラー文言を正確にするため必ず参照） |
| 出力 | `output/{ID}/step3-testcases.md`（雛形：`assets/step3-testcases.template.md`） |
| 検査 | `scripts/check_testcases.py --viewpoints output/{ID}/step2-viewpoints.md` |
| 次 | 完了報告 |

## ロール

QA エンジニアとして、確定した観点ファイルを、テスターがそのまま実行できるケースに展開する。新しい観点は足さない。足すべきものに気づいたら、ケースにせず完了報告で QA に伝える。

## 手順

1. ゲート2 の後に QA が観点ファイルを直していることがある。必ずファイルを読み直してから始める。
2. 観点の形ごとにケースへ広げる：DT は R の列ごと、確認パターン表はデータ行ごと、表の無い観点は 1 ケース以上。
3. 対象外の行は「対象外であることを確かめる」ケースにする。境界値の各行は別々のケースにする。
4. 大項目ごとに 1 つの表にまとめる（TP ごとに表を分けない）。見出しは `### [Step 2 と同じ大項目名]`。
5. 15 列を下の表に従って埋める。
6. 末尾に、ケース数サマリー、観点 → ケース展開トレース表（TP × 表ごとに 1 行。足りなければ ⚠️ と理由）、予測との比較を書く。
7. 最後のケース ID を `<!-- 最終ケースID: ... -->` で残す。何回かに分けて作るときは、次の回はこの ID の続きから始める。

## 15 列の埋め方

列は固定で、増やしたり名前を変えたりしない（テストケース管理 DB のプロパティ名に合わせてある）。

| 列 | 埋め方 |
| --- | --- |
| CaseNo. | `{PBI ID}-TC-001`。3 桁ゼロ埋めの、文書全体の通し番号。1 行から複数ケースを作るときも枝番にしない |
| 観点ID/Viewpoint ID | 元になった `TP-###` |
| タイトル/Title | 確かめる内容を 1 行で。手順や結果の要約は書かない |
| 領域/Area | `.qa/product.md` の領域コード。決める順は PBI に書かれた領域 ＞ Step 1 で特定した領域。全ケース同じ値 |
| 確認画面/Screen | ナレッジや仕様書にある正確な画面名 |
| 機能/Function | 今回の PBI の主な機能名 |
| 大項目/Category | Step 2 の大項目名をそのまま写す |
| 中項目/Sub category | サブ機能やグループ。無ければ `-` |
| 小項目/Item | 具体的な操作、UI 要素、アクション |
| 実施ユーザー/Execution Role | 下の「実施ユーザーの決め方」に従う |
| 事前条件/Precondition | `・` と `<br>` の箇条書き。DT から来たケースは、その R 列の条件の値を写す（例：`・ロール = DUMMY管理者`） |
| 実施手順/Execution Step | `1.` `2.` の番号付きで 3〜5 ステップ |
| 期待結果/Expected Result | `・` と `<br>` の箇条書き。**Step 2 の太字セルをそのまま写す**（要約も創作もしない） |
| 重要度/Priority | Step 2 の TP の優先度（High／Medium／Low） |
| 備考/Remarks | 列は出すが、セルは空のまま（`-` や `N/A` も書かない） |

## 実施ユーザーの決め方

上から順に、最初に当てはまったものを使う。ロール名は `.qa/product.md` のロール表の名前を使う。

1. 条件の軸にロールや権限がある → その値
2. 管理画面での設定操作 → 設定権限を持つロール
3. 業務のロールで決まる → そのロール名、または `ロールなし`
4. 決められない → 空欄

`ロールなし`（ロールが割り当てられていない）と `権限なし者`（ロールはあるが必要な権限が無い）は区別する。

## ルール

- ナレッジにある別の機能をテストするケースは作らない。
- 1 行に複数の画面や操作がまとまっていたら、複数のケースに分け、トレース表に理由を書く。
- `[要確認]` が残っている行も、ケースにしたうえで期待結果に `[要確認]` を残す。消すと、未決の仕様が決まったように見える。
