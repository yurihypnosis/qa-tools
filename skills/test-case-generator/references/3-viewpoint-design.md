# 3. 観点設計

## 契約

| 項目 | 内容 |
| --- | --- |
| 入力 | `output/{ID}/2-analysis.md`（分析レビューで QA が確認したもの）、`PBI/{ID}/`（受入基準があれば確定した入力として扱う）、`.qa/knowledge/` |
| 出力 | `output/{ID}/3-viewpoints.md`（雛形：`assets/viewpoints.template.md`） |
| 検査 | `scripts/check_viewpoints.py`（`references/review-gates.md` の手順で実行） |
| 次 | 観点レビュー |

## ロール

対象プロダクトの QA エンジニアとして、観点と、その下に置く DT／確認パターン表をまとめて設計する。ここで作る表の **1 行がケース生成の 1 ケース以上** になる。観点ファイルは、テストケースの設計図である。

## 手順

1. 分析レビューで QA が決めた衝突の扱いと、`[要確認]` への回答を反映する（会話に回答があればテスト分析のファイルも差分 Edit で更新してから進む）。
2. 大項目を機能のまとまりごとに立てる（例：中心となる機能の挙動／付随する UI／既存機能との整合／他の仕様との相互作用／設定との連携／特殊なデータ／リリース・有効化の境目）。見出しは `## 大項目N: [名前]`。
3. 各大項目の下に `### TP-###: 観点名 【High/Medium/Low】` を立てる。番号は文書全体の通し番号で、大項目が変わってもリセットしない。
4. 観点ごとに表の形を決める。

   | 表 | 使うとき | 形 |
   | --- | --- | --- |
   | DT-x | 条件が 2 軸以上で、組み合わせによって結果が分かれる | 行＝条件と期待結果、列＝R1〜Rn |
   | 確認パターン表 | 条件は 1 軸だが、3 パターン以上を並べる（境界値・状態遷移・対応表・エラー一覧など） | 行＝パターン、列＝属性と期待結果 |
   | 表なし | 単発の確認 | 文章だけ |

5. TP の中に、確かめる内容の文章（必須）、前提の引用、DT／確認パターン表、補足の観点、具体例、`> **対応AC**: AC-###`（受入基準があれば必須）を置く。受入基準に無い観点には `> **対応AC**: なし（AC 未記載の観点。AC 側の抜け候補）` と書く。
6. ナレッジから来た影響確認の観点は Low にして、削らずに出す。
7. 末尾にサマリーを書く：大項目ごとの観点数、ナレッジ由来の観点、受入基準のカバレッジ表、サイズ予測との比較。

**観点数の目安**（上限ではない）：XS 5〜10、S 10〜20、M 20〜40、L 40〜60、XL 60〜80

## 出力のルール

- **期待結果のセルは太字にする。** ケース生成は太字のセルだけを期待結果に写す。太字が無いと、期待結果が要約や創作で埋まる。
- **見出しにしてよいのは大項目（`##`）と TP（`###`）だけ。** DT や表のタイトルは `**DT-1: ...**` のように太字で書く。見出しにすると TP の範囲が途切れ、ケース生成とスクリプトが表の所属を誤る。
- 省略・削除・創作をしない。対象外の行も残す（ケース生成で「対象外であることを確かめる」ケースになる）。不明な点は `[要確認]`。
- R の列どうしは、互いに重ならないか、独立させる。重なると同じケースが二重にできる。
- 同じ確認を複数の TP に散らさない。参照で済むときは別の TP を立てない。
- 共通の表で確かめる観点は `### TP-010〜012: [まとめた名前] 【High】` のように 1 つにまとめてよい。ケース生成では TP ごとに別々のケースを作る。
- 計算が関わるときは、具体例をコードブロックで書いてよい（コードブロック内は検査の対象外）。
