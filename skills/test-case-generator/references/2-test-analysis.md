# 2. テスト分析

## 契約

| 項目 | 内容 |
| --- | --- |
| 入力 | `output/{ID}/1-sizing.md`、`PBI/{ID}/` の全ファイル、`.qa/product.md`、`.qa/knowledge/`（あれば） |
| 出力 | `output/{ID}/2-analysis.md`（雛形：`assets/analysis.template.md`） |
| 検査 | なし（テスト分析には機械的に直せる項目が無い） |
| 次 | 分析レビュー（`references/review-gates.md`） |

## ロール

経験豊富なテストアナリストとして、観点を作る前の「理解」と「絞り込み」を固める。ここでの読み違いは観点設計とケース生成に増幅して伝わるので、早く・安く止めるための工程である。

## 手順

### STEP A：入力どうしの食い違いを見つける（最初に必ず行う）

1. 次の項目を、資料をまたいで突き合わせる：UI 要素の名前、操作の流れ・画面遷移、ステータス名・選択肢・上限値、エラー文言、要素があるかないか。
2. **複数の資料に書かれていて内容が矛盾するときだけ**衝突として挙げる。片方にしか書かれていなければ、その記述を採る（衝突ではない）。
3. 優先順位は「PBI の仕様書 ＝ 受入基準 ＝ 今回のデザイン ＞ ナレッジ ＞ その他」。ナレッジは今回の変更前の仕様なので、PBI と違うのは当然であり、衝突として挙げない。
4. どちらを採るかは決めない。決めるのは QA である。AI が決めると、誤った方を採ったときに誰も気づけない。
5. 衝突があれば、雛形の「⚠️ インプット衝突アラート」を先頭に置く。無ければその節ごと消す。

### STEP B：テスト分析のまとめ

雛形の 1〜6 節を埋める。

1. 要件定義からわかったこと（ビジネスの目的／主な機能と範囲／制約）
2. UI 仕様からわかったこと（画面の構成／主な操作の流れ／UI・UX の注意点）
3. 実装仕様からわかったこと（処理のロジック／外部との連携／技術的な制約。画面に影響する範囲だけ）
4. 全体としての理解（機能の本質を 1 文、最も大事な観点 3〜5 項目、リスク分析の表）
5. PBI のサイズからの予測（観点の数とケースの数）
6. テスト戦略の絞り込み（重点を置く領域／軽めにする領域／省く領域）

**リスクレベルの決め方**

| リスクレベル | 条件 |
| --- | --- |
| Critical | 影響度 High × 発生確率 High |
| High | High × Medium、または Medium × High |
| Medium | 上記以外の組み合わせ |
| Low | 影響度 Low または発生確率 Low |

**サイズ**：`1-sizing.md` の QA 算出サイズを使う。開発サイズと違う場合でも、テストの工数を表しているのは QA 算出サイズだからである。

**ケース数の目安**：XS 10〜20、S 20〜40、M 40〜80、L 80〜150、XL 150 以上

## ルール

- 分析の中心は今回の変更による差分。ナレッジにあっても変更が無い機能は対象外にする。ナレッジは画面名・文言を正しく書くための背景知識である。
- 各セクションは 2〜3 文、または箇条書き 3〜5 項目にまとめる。読むのは QA であり、長い分析はレビューを遅らせる。
- 情報が足りなければ `[要確認]` と書く。推測で埋めると、もっともらしい誤りがレビューをすり抜ける。
- QA の対象外：API テスト、バックエンドの単体テスト、非機能テスト（性能・負荷・セキュリティ・可用性・アクセシビリティ）。非機能テストの観点数は原則 0。
- 対象外にしないもの：ネットワークが届かない・遅いときの画面の挙動（ブラウザの開発者ツールで再現できる範囲）、レスポンシブ表示、仕様に書かれた上限値。
