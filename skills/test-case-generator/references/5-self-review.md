# 5. セルフレビュー

## 契約

| 項目 | 内容 |
| --- | --- |
| 入力 | `output/{ID}/3-viewpoints.md`、`output/{ID}/4-testcases.md` |
| 出力 | `output/{ID}/5-review.md`（雛形：`assets/review.template.md`）。自己修正したときは `4-testcases.md` も更新する |
| 検査 | `scripts/check_viewpoints.py` と `scripts/check_testcases.py --viewpoints` |
| 次 | 完了報告 |

## ロール

作った本人ではなく、**初めて読むレビュアー** として成果物を確かめる。作ったときの思い込みを持ち込まないよう、記憶ではなくファイルを読み直して判断する。

## 手順

1. 2 つの検査スクリプトを `--json` 付きで実行し、レシートを残す。

   ```bash
   python3 <skill>/scripts/check_viewpoints.py output/{ID}/3-viewpoints.md --json
   python3 <skill>/scripts/check_testcases.py output/{ID}/4-testcases.md --viewpoints output/{ID}/3-viewpoints.md --json
   ```

2. スクリプトでは見られない項目を、ファイルを読み直して確かめる（下の「目で見る項目」）。
3. ケースファイルに問題があれば、**1 回だけ** 差分 Edit で直し、2 つのスクリプトをもう一度実行する。
4. 雛形どおりに `5-review.md` を書く。直したこと、直せずに残った問題を分けて書く。

## 機械で見る項目（スクリプトのレシートをそのまま使う）

| 区分 | 項目 | 指摘コード |
| --- | --- | --- |
| A. 観点 | 期待結果のセルの太字、見出しのレベル | `BOLD`、`HEADING` |
| B. ケース | 15 列、CaseNo. の形式と連番、観点 ID の形式、備考が空 | `COLUMNS`、`ROW_WIDTH`、`CASE_ID`、`SEQUENCE`、`VIEWPOINT_ID`、`REMARKS` |
| B. ケース | 観点の表の行数に対してケースが足りているか、存在しない TP を参照していないか | `TRACE`、`UNKNOWN_TP` |
| B. ケース | 期待結果が観点の太字セルの写しか | `EXPECTED` |

## 目で見る項目

| 区分 | 項目 | 確かめること |
| --- | --- | --- |
| A. 観点 | 表の使い分け | 2 軸以上の条件は DT、1 軸 3 パターン以上は確認パターン表になっているか |
| A. 観点 | R 列の独立 | DT の R 列どうしが重なっていないか |
| A. 観点 | サマリー | 大項目別の観点数、AC カバレッジ、予測との対比があるか |
| B. ケース | 大項目の転記 | ケースの大項目名が観点ファイルと一致するか |
| B. ケース | トレース表 | ケースファイル末尾のトレース表の数が、スクリプトの数え直しと一致するか |
| B. ケース | ケースの中身 | 手順が 3〜5 ステップか、実施ユーザーが `.qa/product.md` のロール名か、事前条件だけで再現できるか |
| C. 重複・分けすぎ | TP の重複 | 同じ確認が複数の TP に散っていないか |
| C. 重複・分けすぎ | 機械的な分割 | ON/OFF だけの違いで、意味の無いケースを増やしていないか |

## 直してよい範囲

- 直すのは **ケースファイルだけ**。観点ファイルは観点レビューで QA が確定させたものなので、ここで書き換えない。観点側の問題は「残った問題」として報告する。
- 直すのは、観点ファイルを正としてケースを合わせる修正だけ（期待結果を太字セルに戻す、足りないケースを足す、連番を振り直す、など）。新しい観点やケースの内容を創作しない。
- 自己修正は 1 回まで。直してもスクリプトの指摘が残るなら、それ以上は直さずに報告する。同じ箇所を何度も直すと、もっともらしい誤りが積み上がるからである。
