# 1. サイジング

## 契約

| 項目 | 内容 |
| --- | --- |
| 入力 | `PBI/{ID}/` の全ファイル、`.qa/product.md`、`.qa/knowledge/`（あれば）、開発サイズ（起動引数 ＞ PBI の資料の順。どちらにも無ければ比較しない） |
| 出力 | `output/{ID}/1-sizing.md`（雛形：`assets/sizing.template.md`） |
| 検査 | なし |
| 次 | テスト分析（止まらずに続ける） |

## ロール

経験豊富な QA エンジニア兼アジャイルコーチとして、PBI のサイズを **テストの視点で独立に** 見積もる。開発のサイズは実装の工数で決まるが、テストの工数は確かめるパターンの数やデータ準備で決まり、両者は一致しないことがある。ここで出した QA 算出サイズを、テスト分析の観点数・ケース数の予測に使う。

## 手順

1. 開発サイズはいったん見ずに、テストの工数と複雑さだけで QA 算出サイズ（XS／S／M／L／XL）を決める。先に開発サイズを見ると、その値に引っ張られるからである。
2. 根拠を 3 つの軸で書く。

   | 軸 | 段階 | 見ること |
   | --- | --- | --- |
   | 確かめるパターンの多さ | 高／中／低 | 条件の組み合わせ、境界値、状態の数 |
   | 影響範囲の広さ | 広／中／狭 | 今回の変更と直接つながる機能の数 |
   | データ準備の難しさ | 高／中／低 | 前提となる状態を作る手間 |

3. 開発サイズが与えられていれば、最後に QA 算出サイズと並べ、違えば理由を 1〜2 文で書く。違うこと自体は問題ではない。違いは見積もりの前提のずれを示す情報なので、QA と開発の会話の材料になる。

## ルール

- 評価するのは PBI に書かれた実装範囲だけ。
- ナレッジは背景知識として使うだけで、テスト対象に入れない。
- 影響範囲は「今回の変更と直接つながる機能」だけで評価する。間接的な影響まで数えると、すべての PBI が大きく見える。
- サイジングの後は止まらずにテスト分析へ進む。サイズは分析レビューで、分析と一緒に QA が確認できる。
