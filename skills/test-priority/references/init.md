# init — 設定ファイルを作る

## 契約

| 項目 | 内容 |
| --- | --- |
| 入力 | 利用側プロジェクトのテストケースの表。`.qa/product.md`（あれば、領域コードの確認に使う） |
| 出力 | `.qa/test-priority.toml`（雛形：`assets/test-priority.template.toml`） |
| 検査 | 作った設定ファイルで `load_cases.py` が動くこと |
| 次 | 動詞 `build`（SKILL.md の動詞の表） |

## ロール

QA エンジニアの相談相手として、機能の重みとリスク軸を、QA に質問しながら決める。値を勝手に決めない。QA が答えなかった機能は、領域の `default` を使う（出力で `推定` の印が付く）。

## 手順

1. `.qa/test-priority.toml` が既にあれば、上書きしてよいか確かめる。だめなら止まる。
2. プラットフォーム定義を選ぶ。選択肢は `ls <skill>/platforms/` のディレクトリ名から作る（この reference や SKILL.md には書かない）。1 つしか無ければ、それを使うと伝える。
3. テストケースの置き場所（glob）を、QA に聞く。
4. 次を実行して、領域・機能・画面の件数を調べる。

   ```bash
   python3 <skill>/scripts/survey.py --platform <手順 2 の名前> --glob "<手順 3 の glob>" --root .
   ```

   終了コードが 2 なら、メッセージを QA に見せて止まる。
5. 領域ごとに、次を 1 領域ずつ質問する（1 度に 1 領域）。
   - **リスク軸**：その領域で、重要度を上げる根拠にするもの（`data` データの正しさ、`permission` 権限の境界、`blast` 影響の広がり）。複数可。選択肢の説明は `docs/design/glossary.md` の「リスク軸」と同じ言葉で書く
   - **default**：機能が表に無いときの開始点（1〜4。1 が最も重要）
   - **機能ごとの開始点**：調べた機能の一覧を見せ、QA が知っているものだけ 1〜4 で答えてもらう。答えなかったものは書かない
6. `group_by`（代表を 1 件に絞る単位。`feature` か `screen`）を聞く。調べた結果で、1 つの機能に全ケースが集まっているなら、`screen` を勧める（1 つの機能だと、代表が全体で 1 件しか選ばれないため）。
7. 対象外にする機能があれば聞く（無ければ空）。
8. `assets/test-priority.template.toml` を雛形に、Write で `.qa/test-priority.toml` を作る。雛形に無い領域は、`[rules.areas.<領域コード>]` の節を足す。
9. `python3 <skill>/scripts/load_cases.py --config .qa/test-priority.toml` を実行し、終了コードが 0 であることを確かめる。2 なら、メッセージに従って設定ファイルを 1 回だけ直す。
10. 作った設定ファイルを QA に見せ、次は `/qa-tools:test-priority build` だと伝えて終える。

## ルール

- 領域コードは、テストケースに書かれている値をそのまま使う（`.qa/product.md` の領域コードと同じ）。
- 絶対パスや、人によって違う値を設定ファイルに書かない。
- 質問は、答えの選択肢を示して聞く。QA が「分からない」と答えたら、その項目は聞き直さず、`default` に任せる。
