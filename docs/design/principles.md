# 設計の原則

qa-tools のすべてのツールが守るルール。設計や実装で迷ったら、ここに戻る。

- **読む人**：qa-tools を設計・実装・レビューする人と AI
- **状態**：v0.4.0 時点。実装済みのツールは test-case-generator だけ。例に出てくる他のツールは未実装（[glossary.md](glossary.md) の「ツール名」を参照）
- **言葉**：太字の用語は [glossary.md](glossary.md) で定義している
- **ルールの強さ**：「必須」は守らなければならない。「禁止」はしてはならない。どちらも、外すときは PR に理由を書く

具体的な形（ファイル名・キー・JSON の項目）は [contracts.md](contracts.md)、ツール同士が読むファイルは [data-flow.md](data-flow.md) にある。

## 一覧

| ID | ルール | 強さ |
| --- | --- | --- |
| P1 | 2 つ以上のツールが使う処理は **core** に 1 つだけ置く | 必須 |
| P2 | 製品ごとの値を `skills/` に書かない | 禁止 |
| P3 | 同じ入力から同じ結果になる処理は、AI ではなく Python スクリプトで行う | 必須 |
| P4 | **検査**に通らなかった成果物を「最新」として **manifest** に記録しない | 禁止 |
| P5 | 決められない値を推測で埋めない。**未解決マーカー**を書く | 禁止 |
| P6 | **差分更新**では、入力が変わっていない**項目**を作り直さない | 禁止 |
| P7 | すべての**出力ディレクトリ**に manifest を置く | 必須 |
| P8 | 他のツールの**公開ファイル**以外の出力を読まない | 禁止 |
| P9 | 測っていない数値を、決定済みの値として書かない | 禁止 |

## P1. 2 つ以上のツールが使う処理は core に 1 つだけ置く（必須）

- **ルール**：同じ処理を 2 つ目のツールが必要としたら、その処理を `core/` に移し、両方のツールが `core/` を呼ぶ。1 つのツールしか使わないうちは、そのツールの `scripts/` に置いてよい
- **確かめ方**：`skills/*/scripts/` に、同じ役割の関数が 2 つ以上ないこと
- **例**：manifest の読み書きは test-steps と code-map の両方が使うので、`core/manifest.py` にだけ置く
- **理由**：同じ処理を各ツールが持つと、1 か所を直したときに他を直し忘れる

## P2. 製品ごとの値を skills/ に書かない（禁止）

- **ルール**：製品名、チケット接頭辞、領域、ロール、機能の重み、プラットフォームの選択は、**利用側プロジェクト**の `.qa/` に書く。`skills/` の下で、これらの値を判定・分岐・既定値に使ってはならない。説明の「例」として書くのはよい（例：起動例の `PBI: DUMMY-001`）
- **確かめ方**：ダミー製品の `.qa/` の値（ロール名など）を別の値に書き換えて E2E を実行し、出力に元の値が 1 つも出ないこと
- **例**：test-case-generator はロール名を `.qa/product.md` から読む
- **理由**：skill に製品の値を書くと、別の製品で使うたびに skill を書き換えることになり、他の製品の結果が変わる

## P3. 同じ入力から同じ結果になる処理は Python スクリプトで行う（必須）

- **ルール**：ファイルの列挙、分割、結合、形式の検査のように、答えが 1 つに決まる処理は、標準ライブラリだけの Python スクリプトで行う。AI に任せるのは、意味の判断（「これは画面か」「この手順は何を確かめているか」）だけ
- **確かめ方**：skill の手順（SKILL.md と references/）で、AI に「ファイルを数えて」「表を結合して」と指示している箇所が無いこと
- **例**：code-map の import の抽出は `extract.py` が行う。モジュールの要約文だけを AI が書く
- **理由**：AI は同じ入力でも毎回少し違う結果を出す。スクリプトにできる範囲を広げるほど、結果のぶれとコストが減る

## P4. 検査に通らなかった成果物を manifest に記録しない（禁止）

- **ルール**：`build` と `update` は最後に必ず検査を実行する。検査結果の `status` が `fail` なら、manifest を書き換えずに止まり、検査結果を人に見せる
- **確かめ方**：検査が失敗する fixture で `build` を実行し、manifest.json の更新日時が変わらないこと
- **例**：手順書の「補足」セクションが抜けていたら、test-steps は manifest を更新しない
- **理由**：失敗した状態を manifest に記録すると、次の `update` が壊れた成果物を前提に差分を取る
- **限界**：検査で分かるのは形式と件数まで。内容が正しいかは保証しない。各ツールの README にこの限界を書く

## P5. 決められない値を推測で埋めない（禁止）

- **ルール**：入力に情報が無くて値を決められないときは、それらしい値を書かずに、未解決マーカー `[未解決: 理由]` を書く。理由には「何が無いから決められないか」を書く
- **確かめ方**：検査スクリプトが未解決マーカーの件数を数え、検査結果の `stats` に出す。件数が 0 でも 1 以上でも検査は通る（件数を人が見る）
- **例**：Playwright の spec が import するファイルが見つからない → `[未解決: helpers/auth.ts が見つからない]`
- **理由**：推測で埋めた値は、正しい値と見分けがつかない。後の工程がその値を前提に作られる
- **同じ考え方の既存の例**：test-case-generator の `[要確認]`

## P6. 差分更新では、入力が変わっていない項目を作り直さない（禁止）

- **ルール**：`update` では、入力が変わっていない項目を前回の出力から写す（**引き継ぎ**）。AI に作り直させない。同じ項目かどうか機械で決められないとき（ファイル名が変わったなど）は、人に聞き、答えを**裁定**として記録する
- **確かめ方**：入力を何も変えずに `update` を実行し、manifest.json 以外の出力が 1 バイトも変わらないこと
- **例**：テストケースを 1 件だけ書き換えて test-priority を `update` すると、他のケースの判定は前回のまま残る
- **理由**：AI に作り直させると、入力が同じでも名前や判定が変わる。変わると、前回との比較も、他のツールとの突き合わせもできなくなる

## P7. すべての出力ディレクトリに manifest を置く（必須）

- **ルール**：`output/<ツール名>/manifest.json` を必ず置く。項目は [contracts.md の C5](contracts.md#c5-manifestjson) で決めたもの。設定ファイルが無い・壊れているときに、既定値で黙って続けない（止まって伝える）
- **確かめ方**：検査スクリプトが manifest の有無と必須項目を確かめる
- **例**：`update` は manifest の `source.commit` から今のコミットまでの差分を取る
- **理由**：いつ・何から作ったか分からない成果物は、QA の判断材料として信用できない。差分更新の起点も無くなる
- **例外**：test-case-generator は v0.4.0 より前に作ったため、まだ manifest を置かない

## P8. 他のツールの公開ファイル以外の出力を読まない（禁止）

- **ルール**：ツール A がツール B の出力を読むのは、[data-flow.md](data-flow.md) の表に載っている公開ファイルだけ。表に無いファイルが必要になったら、先に表を更新する PR を出す
- **確かめ方**：skill の手順と scripts の中で、他のツールの `output/<ツール名>/` を参照している箇所が、すべて data-flow.md の表にあること
- **例**：screen-list は code-map の `lookup/routes.jsonl`（公開ファイル）を読む。`_raw/`（中間ファイル）は読まない
- **理由**：公開していないファイルに他のツールが依存すると、作る側がそのファイルを変えられなくなる

## P9. 測っていない数値を決定済みの値として書かない（禁止）

- **ルール**：しきい値（「何割変わったら全部作り直すか」など）は、測るまで「仮の値」と明記する。仮の値は、設定ファイルで変えられるようにする
- **確かめ方**：設計文書と設定の既定値で、数値の横に「仮」か「測定済み（測定した Issue の番号）」のどちらかが書いてあること
- **例**：code-map で全体を作り直す条件「モジュールの半分以上が変わった」は仮の値
- **理由**：測らずに決めた値は、品質を落としていても気づけない
- **関連**：ローカル LLM のような効果が未確認の仕組みは `experimental/` に置き、動詞やオプションを増やさない
