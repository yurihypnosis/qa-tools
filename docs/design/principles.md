# 設計の原則

qa-tools のツール（test-case-generator、test-steps、test-priority、code-map、screen-list）が共通して守る考え方。新しいツールを足すときや、判断に迷ったときはここに戻る。

約束ごとの具体的な形（動詞・設定・manifest など）は [contracts.md](contracts.md)、ツール同士の受け渡しは [data-flow.md](data-flow.md) にある。

## 1. 地図を作り、ソースが変わったら差分だけ描き直す

code-map・screen-list・test-steps は、どれも「ソースを読み、人と AI が使える地図を作る」道具で、違うのは何の地図を描くかだけである。だから骨格（差分の計画、引き継ぎ、検証、身元書き）は 1 つにし、各ツールは「何を抜き出し、どう書き、何を検証するか」だけを持つ。

- 理由：骨格をツールごとに持つと、同じ処理が少しずつ違う形で増え、直すときに全部を追うことになる
- 例：差分の計画は `core/plan.py` にだけあり、test-steps も code-map も同じものを呼ぶ

## 2. 汎用の仕組みと、製品ごとの設定を分ける

skill は製品の名前も業務も知らない。製品ごとの値（チケット接頭辞、領域、機能の重み、プラットフォーム）は、利用側の `.qa/` に置く。

- 理由：製品を足すたびに skill を書き換えると、別の製品の結果が変わってしまう。足すときは設定を書くだけで済むようにする
- 例：test-case-generator はロール名を `.qa/product.md` から読む。test-priority は機能の重み表を `.qa/test-priority.toml` から読む

## 3. 決まった処理はスクリプト、意味の判断だけ AI

ファイルの列挙、分割、結合、形式の検査は、標準ライブラリだけの Python スクリプトで行う。AI には「これは画面か」「このテストは何を確かめているか」のような、意味の判断だけを任せる。

- 理由：同じ入力なら同じ結果になる範囲を広げるほど、AI の揺れとコストが出る範囲が狭くなる
- 例：code-map の extract（ファイルツリー、import、シンボル）は LLM を使わない。モジュールの要約だけを LLM が書く

## 4. AI の出力は、機械のゲートで検めてから使う

AI が「できた」と言っても、そのまま採用しない。コードから機械的に数えた「あるはずのもの」や、決めた形式と突き合わせてから使う。ゲートを通らなければ、成果物を「最新」として記録しない。

- 理由：AI の自己申告の確信度は当てにならない。ただし、誤検知だらけのチェックはやがて無視されるので、期待値があいまいなものは検査しない
- 限界：機械のチェックで分かるのは「形と件数」までで、意味の正しさまでは保証しない。そのことを成果物の README に書く
- 例：screen-list は、ルート定義から数えた画面と CSV の行を突き合わせ、漏れを報告する

## 5. 決められないものは推測で埋めない

情報が足りないときは、それらしい値で埋めずに、決められない理由を書いて人に返す。

- 理由：推測で埋めた値は、正しい値と見分けがつかない。後の工程がそれを前提に積み上がる
- 例：test-steps の `[未解決: 理由]`、test-priority の「判定不可」、test-case-generator の `[要確認]`

## 6. 作るたびに結果を揺らさない

変わっていない部分は前回の判断を引き継ぎ、変わった部分だけを作り直す。同じ項目かどうか迷うものは、勝手に寄せずに人が裁定し、その裁定を記録して次回も使う。

- 理由：AI に丸ごと作り直させると、ソースが変わっていなくても名前や判定が揺れる。揺れると過去との比較も、他のツールとの連携も壊れる
- 例：test-priority は、内容が変わっていないテストケースの判定を前回のまま残す

## 7. いつ・どの設定で作ったかを必ず記録する

すべての成果物の横に `manifest.json` を置き、対象のコミット（または入力のハッシュ）、設定のハッシュ、生成日時、誰が何件作ったかを残す。設定があいまいなときに、黙って既定値に切り替えることもしない。

- 理由：鮮度と出どころが分からない成果物は、QA の判断材料として信用できない。差分更新の起点にもなる
- 例：`update` は manifest の commit から今のコミットまでの差分だけを作り直す

## 8. 他のツールが依存してよい範囲（契約）を決めて渡す

成果物のうち、他のツールが読んでよいファイル・列・語彙を「契約」として決め、それ以外（中間データ）は読ませない。使う側に合わせた加工済みの索引は作らず、使う側がそれぞれ変換する。

- 理由：契約外のファイルに依存されると、作る側が中身を変えられなくなる。共通の加工済み索引は、使う側ごとに必要な形が違うので誰にも最適にならない
- 例：code-map の `_raw/` は契約外。screen-list は `lookup/routes.jsonl`（契約内）だけを読む

## 9. コストを削るのは、品質を落とさない範囲で、測ってから

ローカル LLM への委譲や、しきい値の調整は、実際に測ってから決める。測っていない値は「仮」と書き、期待値で導入を決めない。実験中の仕組みは `experimental/` に置き、普段の入口に出さない。

- 理由：効果を測らずに入れた最適化は、品質を落としていても気づけない
- 例：code-map で全体を作り直す条件（「モジュールの半分以上が変わった」）は仮の値として置き、測って見直す
